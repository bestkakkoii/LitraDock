# Bounded pilot retirement

The supported pilot uses one systemd application supervisor, a separate expiry timer that stops admission, and a later root retirement timer. The application checks its configured expiry itself. Actual registration, dates, database OID, unit definitions, host paths and credentials belong in protected operator records; no deployment is inferred from this companion tool.

`python3 deployment/qualification/retire_demo.py --config /etc/literature/deployment.json` only checks registration and storage guards and reports DUE when eligible. It does not probe the database or claim successful retirement. `--apply` is the explicit destructive operation for the registered, disposable pilot. The protected registration contains `id` (`deploymentNNN-YYYYMMDD`), `database` (`literature_demo_YYYYMMDD`), `databaseOid` (original positive integer), `role` (`literature_demo`), `dataRoot` (`/srv/literature-demo`), and timezone-qualified `createdAt`, `expiresAt`, `deleteAfter`, strictly ordered and at most30 days apart. The actual policy must match the user-visible promise; placeholders are not deployment evidence.

On Linux as root, the command validates private paths, rejects links/special files/unexpected root members, takes a nonblocking exclusive registration lock, stops the one service, and refuses remaining service-user processes. It checks the original database OID and owner through PostgreSQL18 local peer administration. Only then does it disable connections, terminate that database's sessions, drop it, remove its dedicated objects/recovery directories and remove the protected service/invitation configuration. It preserves unrelated databases and code, and does not infer permission from a similarly named replacement database. The application unit must have `ConditionPathExists` for its protected environment so later restart cannot recreate a retired pilot.

The private binding journal records deleting, database-removed and complete phases. A retry after interruption can finish the same registration; a new database OID or post-retirement data refuses cleanup. Partial filesystem deletion is possible on failure: retain the private journal and inspect before retrying the same command. The atomic journal rename is not a demonstrated power-loss/fsync guarantee. Root or other out-of-band writers must remain quiescent throughout retirement. This is not a general-purpose tenant deletion API, secure disk erasure, off-host backup deletion, automatic account recovery or proof that a future scheduled timer has executed.

Reproduce safe registration controls with `python3 tests/deployment/test_retire_demo.py`. The actual deployment additionally exercised a separate Linux root, disposable PostgreSQL18 database and control service, including wrong OID, simulated interruption after database drop, replacement-database refusal, partial retry and completed-state replay. The protected target procedure records exact scope and receipts. Never redirect those controls at production or infer target permission from this document. Restored clones and any additional backups must be removed or explicitly included in the same actual retention procedure.

# ADR0026 — evidence-bound source outcomes and PDF handoff

Status: proposed candidate for native021 independent review; not release acceptance.

The original PDF action admitted work but left the result below the viewport and did not hand a file to the browser. The native019 retained evidence also distinguished an empty permitted deposit from manuscript/TDM metadata, while the saved outcomes used broad holds. CHG0054 requires immediate local feedback and an actual acquire-to-file path; metadata availability grants no new rights.

Schema8 is retained. Exact persisted diagnostic messages map to structured `sourceOutcome` fields; unknown older reasons remain held. The complete listing parser distinguishes zero, multiple and incomplete listings without selecting a highest version. Metadata identity is checked before classifying manuscript/TDM. Search results read only their library's saved history and original descriptors. A descriptor means stored, not validated or ready; current batch/plan/file checks establish download availability. Direct source links derive from separate PMID, PMCID and DOI values, never arbitrary stored URLs. CSV/XLSX append outcome fields; structured and ZIP manifests retain per-member outcomes and explicit scope. Existing frozen snapshots are not rewritten.

A PDF click captures immutable selection, library, run, session generation and idempotency key. It admits one batch or plan, polls only that receipt and hands off one PDF or a ZIP when processing settles and an original is available. A single PDF's current MIME, declared bytes and SHA256 must match before handoff. Batch/plan ZIPs retain existing server integrity checks, 32MiB original-data and 37MiB transport limits. Failed or interrupted transfers require an explicit retry, which reuses the admission receipt. UI rerender, reload and polling do not independently trigger file saves. The browser cannot confirm a disk save, so the message says the file was sent to the browser and offers Save again.

REVIEW044-F1 adds a distinct `pdf-download` export response for the primary multi-record PDF action. The server reads the final bounded ZIP manifest, verifies every selected member, physical PDF entry/hash and exact archive membership, then returns a versioned outcome report bound to the archive SHA256. Framing uses a four-byte big-endian report length, at most1MiB of JSON and at most37MiB of unchanged ZIP bytes. The client validates the immutable selection, batch/plan/run identity, final counts and archive hash before handoff, and replaces earlier readiness with these final outcomes. Zero included PDFs returns no archive bytes and produces no browser download. Ordinary ZIP metadata exports keep their existing behavior. This endpoint reserves the existing single ZIP slot and rechecks session/library admission before writing its response; it neither acquires content nor changes grants.

Feedback, immutable request count and source outcomes stay beside the primary action. No-file results expose reasons and navigation links locally, plus a scoped metadata export. Stop waiting stops client polling/transfer only; existing processing remains visible through saved details with its normal pause/cancel controls. Scope changes and session invalidation discard late results. Broader PubMed layout/filter work and staged large results remain native022; this focused repair does not establish complete usability acceptance.

The private activation plan binds two retained native019 bodies to exact saved attempt identities, metadata digests, original held reasons and observation timestamps. It changes only those saved reasons after a fresh isolated restore test. It never broadens grants, fetches a provider, imports a new original or changes an existing frozen snapshot. Deployment must update the active runtime and native020 backup pins together; rollback restores runtime/configuration only and preserves current research and evidence annotations. No old database restore is permitted over live activity.

REVIEW044-F2 requires durable schedule ownership before each stop. The protected journal records the Task/Dispatch, initially active/enabled state and hash of each timer/service definition, followed by stop intent before the side effect. Recovery starts only unchanged units with owned outstanding stop intents, preserves foreign changes, and supports interruption in the prepared phase without stopping the application. An exclusive journal lock prevents overlapping release/recovery writers. Separate schedule recovery remains available if runtime reconciliation must wait. Actual Linux process-loss fixtures exercise both first/second timer stops and subsequent runtime phases; these are isolated filesystem/systemd mocks, not live outage tests.

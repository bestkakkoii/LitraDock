# ADR-0014: Durable plans over saved records

Decision: extend the native PostgreSQL model with a durable plan, immutable ranked membership and bounded idempotent control receipts. Reuse child batches and the single source worker. No additional queue service, provider permission or client-side acquisition loop is introduced.

Use native schema version 2 with additive plan tables and a nullable plan reference on native_batches. Global acquisition capacity counts native_items plus unmaterialized memberships, so old batch admission and new plans share the same 1000-item envelope. Materializing at most 10 items transfers reservations atomically; unique parent membership and child linkage prevent duplicate scheduling. Global control-receipt retention is bounded separately rather than allowing unlimited idempotency rows.

Lifecycle transactions take the existing capacity advisory lock first, then parent, child and item locks. Completion rechecks parent/child state and the exact lease under those locks before committing bytes. Parent pause/cancel clears child leases and cancels no already preserved originals. Scheduler runs only inside the existing shared recovery and exclusive heavy-work gates. Source request serialization remains the authoritative final budget check; admission conservatively observes cooldown/day/lifetime/storage before creating another child. Round-robin group eligibility uses last_scheduled_at with stable tie breaks.

Use repeatable-read detail snapshots and disjoint historical item counts. Validate current bytes/rights for the returned page separately; do not turn an unavailable current download into a lost historic acquisition or a fabricated plan-wide availability count. Preserve original provenance, identifiers and all existing export selectors. Plan-wide exports are deferred explicitly.

Migration is an explicit stopped-service operator command under exclusive request admission. Bootstrap creates schema 2; the new service requires schema 2 for native databases. Migration preserves all version-1 rows. Empty-plan rollback may drop only the additive structures after proving no plan/membership/control/child references exist, then restore version 1. Once a real plan exists, old005 rollback is refused: retain schema 2 and use a compatible qualified binary or a separately validated data migration. Never overwrite intervening user data with a stale snapshot. Paired backup/disposable restore and exact row/hash comparison are required before deployment.

Idiomatic Go contexts, pgx transactions, constraints and explicit typed JSON use existing dependencies. The release report must separate isolated fault fixtures, genuinely cached original reuse, fresh provider qualification, actual resource measurements and physical-device limitations. Public005 remains unchanged until candidate review and deployment gates pass.

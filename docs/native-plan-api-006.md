# Native processing-plan API v1

Version 1 integration contract for the native processing-plan candidate. Implementation and deployment qualification are separate gates. Existing batch/export/original routes remain unchanged; a plan is not a client loop of batch requests. No plan-wide export selector exists in this increment: open child batches for their supported XLSX/CSV/ZIP and individual Save operations.

All plan routes are under `/api/libraries/{library}/plans`, behind existing owner/session/recovery admission. Every POST requires same Origin, JSON and X-CSRF. Unknown/foreign library, plan, run or record returns 404; invalid syntax returns 400; altered idempotency payload, stale control revision, capacity or lifecycle conflict returns 409; disabled new plan creation returns 409; infrastructure errors return 503 without raw database details. GET never schedules work or spends source requests.

`GET /service-info` adds `planEnabled` (false unless explicitly configured), `planSelectionLimit:100`, `planGroupLimit:10`. Existing `batchLimit:10` and `searchLimit:100` remain. Existing plans can be read and paused/cancelled while creation is disabled; resume/retry require enabled plans. Disabling plans also prevents further plan-child claims/admission. UI may not widen the ordinary batch button to 100.

| Route | JSON and response |
|---|---|
| POST collection | `{requestID:string UUID,runID:string,searchIDs:string[]}`; 1–100 unique explicit saved IDs from the same library/run; returns `{planID,revision,selectedCount,state}` after commit |
| GET collection | `?offset=0&limit=25` (limit 1–100); `{plans:[PlanSummary],total,offset,limit}` ordered by createdAt then planID |
| GET detail | `/{planID}?offset=0&limit=25`; `{plan:PlanSummary,items:PlanItem[],total,offset,limit,nextPollAfterMs:2000,policy:string}` |
| POST control | `/{planID}/control` body `{requestID:UUID,expectedRevision:positive integer,value:"pause"|"resume"|"cancel"|"retry"}`; returns `{planID,revision,state,affectedCount}` after commit |

`PlanSummary`: `{planID,runID,state,selectedCount,createdAt,updatedAt,revision,allowedActions:string[],counts:PhaseCounts,admission:{admittedCount,waitingCount,blockedReasonCode,reason,retryAfter:null|string},retryEligibleCount}`. Times are RFC3339 strings. Revision is a server integer changed by parent control, admission and worker state transitions, not wall time. The POST receipt represents the committed operation, not necessarily the latest state when a replay occurs: GET current detail after success/replay. No private draft or credentials in localStorage.

`PlanItem`: `{searchID,rank,childBatchID:null|string,phase,acquisitionState:null|string,reason,attempts,retryEligible,downloadAvailable,article,original_hash:string,bytes:number,rights_uri:string,source_uri:string,repository_stamp:string,format:string,version:string}`. Article matches the existing metadata contract and safe source links; identifiers stay separate. `downloadAvailable` is checked against current retained bytes/rights, independently of historical acquisition state. Availability is supplied only for returned page items: no guessed plan-wide available count. Counts always cover every plan item in one consistent database snapshot. Details report a temporary failure instead of returning a partially checked page.

`PhaseCounts` always has eight integer fields `waiting,queued,running,completed,held,retry,paused,cancelled` including zeros, whose sum equals `selectedCount`:

- Unmaterialized membership: cancelled membership or cancelled parent -> cancelled; paused parent -> paused; otherwise waiting.
- Child stored state queued/running/paused/cancelled -> corresponding phase; acquired -> completed; unavailable/unsupported -> held; failed/transient/rate_wait -> retry. Unknown state is an explicit protocol error.
- Historical completed is “Acquired on server”, not “downloaded to device”; a current policy downgrade can set `downloadAvailable:false` without changing completed counts. `retryEligible` is true only for the three retry states below three attempts and an active/partial parent.
- `admittedCount` is cumulative unique memberships with a child; `waitingCount` counts uncancelled unmaterialized memberships, including those paused by the parent. It is an admission count, deliberately distinct from the displayed waiting phase.
- Explicit parent paused/cancelled takes precedence. Otherwise all completed -> complete; any waiting/queued/running/paused -> active; otherwise partial. Partial does not imply all originals are available.

Selection equality is run ID plus sorted exact IDs; first admitted display order is retained. Same library/request UUID and same canonical payload replays the original receipt even after progress; changed payload conflicts. Control IDs are scoped to a plan, compare exact action and expectedRevision on replay, and retain the original receipt. Do not generate a new UUID when retrying a lost response; refresh/relogin/reopen use reads only.

Pause applies to active work, stops materialization and invalidates queued/running child leases; previously acquired/held outcomes remain. Resume is only from paused and never resets attempts. Cancel marks never-admitted and unfinished child work cancelled, invalidates leases and preserves terminal originals/reasons; cancelled plans cannot resume/retry. Retry is available only when no child is queued/running/paused and requeues the earliest eligible child group only (at most 10 failed/transient/rate_wait items below three attempts), after source/policy/storage checks; it does not retry held rights. UI follows `allowedActions`, uses explicit cancel confirmation and refreshes after 409 without blind retry against a changed revision.

Backend reservations count every standalone/child native item plus every unmaterialized plan membership against the same global 1000-item limit, including retained cancelled records; child materialization transfers a reservation without double counting. Storage remains 256 MiB. At most one unfinished child per plan; deterministic oldest-last-scheduled plan admission prevents one plan monopolizing groups. The same single worker, heavy/recovery locks, 400ms source spacing, lifetime/day allowances and Retry-After apply. Polls and exports cannot advance plans. A waiting reason distinguishes disabled policy, current cooldown, lifetime/day allowance and storage. A future retry time is emitted only if known.

Frontend behavior: Add a distinct plan action and saved-plan catalog/detail with selected count, phase counts, per-item reasons/source links, child-batch navigation, bounded polling and generation fencing. Preserve ordinary batch 10, source policy and exports. Draft plan selection can reach 100 only with server support; ordinary batch creation remains disabled above 10. Paging retains exact selected IDs; library/run/account/session changes clear them. Poll one request at a time, at least server delay, maximum 120 automatic reads, then manual Refresh; background server work continues. Fence after headers/body and before every UI/file/timer side effect. No synthetic product records or framework migration.

Acceptance: cap 100/101, selected 37 over saved pages versus a synthetic 25001 provider total, no duplicate POSTs on lost-response/relogin/reopen, parent pause/cancel/retry/revision and mixed states, tenant switch/delayed responses, held source links and child original/export paths, desktop and 390px. Qualification separates actual handlers/PostgreSQL/browser integration from focused frontend tests. Exact schema and transaction design are in ADR-0014.
